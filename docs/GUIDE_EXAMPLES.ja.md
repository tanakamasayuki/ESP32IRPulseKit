# IRサンプルの実行と組み込み方

> English: [GUIDE_EXAMPLES.md](GUIDE_EXAMPLES.md)

[サンプル一覧](../examples/README.ja.md)と一緒に読むガイドです。個々の操作や出力は各サンプルのREADMEにあります。導入条件や対応プロトコルは[ライブラリREADME](../README.ja.md)で確認し、ボードやコアを選んでください。

## ハードウェアを準備する

受信には、裸のフォトダイオードではなく、リモコン用の復調型赤外線受信モジュールを使います。VCC・GND・OUTはデータシートで確認してください。端子の並びや使用できる電源電圧は製品ごとに異なります。OUTの信号レベルもESP32の入力条件に合わせます。GNDを共通にし、利用できる入力GPIOを選んで `IRReceiver rx(pin, inverted)` を変更します。例は一般的なactive-low受信器を想定した反転設定です。実際のモジュールが逆の極性なら変更します。例のGPIO番号は配線の一例で、どの基板でも使える端子という意味ではありません。

送信には、赤外線LEDと電流制限、LEDおよび電源に適した駆動回路を用意します。`IRSender tx(pin)` が選ぶのはその回路を制御する信号端子で、LED電流を制限する機能はありません。回路の極性を確認し、基板とGNDを共通にします。コネクタの形や例のGPIO番号から、モジュールの電気的な端子配置を推測しないでください。

ライブラリを導入し、使用する `.ino` を開き、実際のボードとポートを選択して書き込みます。シリアルモニタはスケッチの通信速度に合わせます。まず受信器と正常なリモコンで受信を確認し、その後で送信器を追加すると切り分けが容易です。別の基板で受信例を動かすと送信波形を確認できます。

## 3種類の表現を理解する

- RAWはmark/spaceの時間が交互に並ぶ配列です。`IRRawTickView::len` はバイト数ではなく要素数で、1 tickは10マイクロ秒です。`printRawMicros()` は読みやすい時間表示へ変換します。復調型受信器が取得するのは包絡線なので、RAWから光のキャリア周波数は測れません。
- `IRDecodedBits` はプロトコルID、フレーム種別、ビット長、bitsを持ちます。プロトコル用ヘルパーを使えば、ビット順や冗長フィールドを手作業で組み立てずに済みます。リピートフレームは最初のコマンドと異なることがあります。
- プロトコル固有の `Frame` 型は項目を名前付きで扱います。AC用Frameは独立した `ac` レイヤーにあり、多くの場合、最後に押したボタンだけでなく家電の状態全体を運びます。

## 受信してから内容を調べ、必要なら保存する

`IRReceiver` は `begin()` の前に設定します。新しい配線を立ち上げるときは、初期化が返すboolを確認してください。`loop()` では `read(result)` を繰り返し呼びます。falseなら処理する結果はなく、未初期化でもfalseになります。falseのあとに以前のresultの内容を使わないようにします。

受信できたことと、プロトコルをデコードできたことは別です。候補へアクセスする前に `count` または `candidate()` を確認します。候補はスコア順ですが、点数が高いことだけで元のプロトコルは確定しません。似た結果ならRAWとリピートの挙動も見ます。`setDecodeCandidates(0)` は汎用デコードを意図的に無効にする設定で、AC例は代わりにRAWをACデコーダへ渡します。

`result.raw` は受信器が所有するバッファを参照します。次の `read()` や `end()` で置き換わる前に、表示・デコード・コピーを終えてください。viewをコピーするだけではポインタと長さしか複製されません。学習データを保持する場合はtickの値そのものを自分の配列へコピーします。

`truncated()` と `rmtOverflow()` はその受信の状態を示し、`stats()` ではキュー破棄などの累積回数も確認できます。不完全な波形を再送用の確かなデータとして扱わないでください。長い信号には、十分なシンボル容量と、信号内部の隙間より長いidle閾値の両方が必要です。容量設定は初期化前に行い、設定APIの戻り値も確認します。チップごとの上限は固定値として思い込まず、APIとハードウェアの条件を参照します。

## 送信結果を正しく読む

`IRSender` を設定して `begin()` の成否を確認し、bitsまたはRAW viewを作って `send()` の成否を確認します。波形はハードウェアが生成しますが、**公開APIの `send()` はローカルの送信完了を待って戻ります**。長いACフレームや繰り返し送信では、その所要時間をloopの設計に含めます。完了コールバックで通知されるAPIではありません。

trueはローカルの送信完了を意味し、家電が受信したことまでは示しません。RAW再送には完全な時間列に加え、正しいキャリアが必要です。bitsの送信では `setCarrierHz()` で上書きしない限りプロトコルのキャリアを使います。AC例では既定の位相整合キャリアを使い、モード変更やRMT資源の追加確保はルートREADMEの設定説明を読んでから行います。

リピート引数は追加送信回数です。既定の負値を指定したbits送信ではプロトコルの既定値を使いますが、RAWには繰り返し方を判断するプロトコル情報がありません。間隔や初回／リピートの違いにも意味があり、たまたま取得したリピートだけを連送しても、ボタン操作と同じになるとは限りません。

## 学習で出たコードをアプリへ移す

`04_learn` と `06_ac_learn` はコードを表示する例です。学習内容をフラッシュへ保存したり送信したりはしません。生成された配列／状態と送信式をすべて送信スケッチへコピーし、出力端子とキャリアを設定して初期化してから、元のリモコンと受信内容を比べます。まず短押し1回で確認します。

AC学習では、編集用setterテンプレートと状態バイト版が出ることがあります。setterは温度やモードを変更する用途に便利ですが、不明な項目や未対応項目を省く場合があります。状態バイト版はデコードしたバイトを保持し、RAWは受信した時間列を保持します。いずれも同じブランドの全機種への互換性を保証するものではありません。

## 問題を切り分ける

| 症状 | 確認すること |
|---|---|
| 受信出力がない | 初期化成否、OUTのGPIO、モジュールの端子・電源・GND・極性。正常なリモコンでも試す |
| RAWは出るが候補がない | 未対応プロトコル、ノイズ、リピートの可能性。RAWモニタやAC学習例で確認する |
| ACの1回の操作が複数に分かれる | idle閾値が内部ギャップより短い可能性。数回の操作を比較する |
| 切り詰めやオーバーフローが増える | 受信容量、処理や表示にかかる時間、RMT資源。修正後に取り直す |
| send()がfalse | 送信器の初期化、引数、GPIO、資源や設定の失敗 |
| sentなのに家電が反応しない | プロトコル・機種・状態項目・キャリア・波形の完全性・駆動回路の極性・向き・距離 |

バージョンや対応状況の表はルートREADME、基板や部品の固有情報は各製品の資料を参照します。このガイドと各例は、スケッチで再利用するAPIの使い方と確認方法を中心にしています。
