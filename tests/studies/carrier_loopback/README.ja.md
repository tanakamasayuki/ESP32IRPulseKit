# キャリア ループバック プローブ（1ボード）

> English: [README.md](README.md)

TSOPを経路から外し、**ライブラリが出すキャリアそのもの**を直接観測するリグです。
PulseKit→IRremoteESP8266 の JVC が際どい原因を確定させるのが目的。1ボードが
**キャリア変調されたマーク**の短いパターンをライブラリTXで送信し、**有線ループ
バックした電気信号を 1µs（RMT、復調器なし）で捕捉**するので、キャリアの半周期
ごとに別エッジとして見えます。

配線：**`LOOPBACK_TX_GPIO` → `LOOPBACK_RX_GPIO`** を直結（既定 GPIO5 → GPIO6、
`.env` 反映）。IR LEDもTSOPも使いません。

## 何を切り分けるか

JVCのジッターは送信側に帰属済み。TX側の候補メカニズムは2つあり、このリグで分離します：

- **キャリア周期の量子化** — ライブラリの100kHz（10µs）RMT解像度では 38kHz は
  2.63 tick/周期で割り切れず、周期がディザる可能性。→ **マーク内の周期ばらつき**が大。
- **キャリアのフリーラン位相** — RMTキャリアは連続発振なので、マーク境界での位相が
  マーク毎にドリフトする。→ 同じ幅のマークでも**キャリアON期間/サイクル数がマーク毎に変動**。

## 実行

```sh
cd tests
uv run --env-file .env pytest -s -o python_files="study_*.py" studies/carrier_loopback/
```

`CAP <mark_us> <space_us> <count> [duty_pct] [carrier_hz]` で `count` 本のキャリア
マークを送り、生1µsキャプチャをダンプ。環境変数で上書き：
`CL_MARK`(530)/`CL_SPACE`(530)/`CL_COUNT`(4)/`CL_DUTY`(33)/`CL_HZ`(38000)/
`CL_SENDS`(20)/`CL_OUT`(`data/carrier_loopback.txt`)。

パターンは短く：キャリアONだと26µsごとに1エッジ対が出て、捕捉は
`RMT_MEM_NUM_BLOCKS_4`（約192シンボル）が上限。4×530µs（約80サイクル）は安全。
フルフレームは溢れる。

## 出力 / 解析

テストはサマリを表示し、生ダンプを `data/` に保存。オフライン再解析（プロット）：

```sh
uv run --with matplotlib python studies/carrier_loopback/analyze.py \
  studies/carrier_loopback/data/carrier_loopback.txt --plot out.png
```

主な項目：

- `carrier period: mean .. within-mark sd ..` — 周期の綺麗さ。sdが大（>~2µs）なら
  **TX解像度**ディザが疑わしい。
- `cycles/mark` と `carrier-on span sd` — マーク毎のばらつき。非ゼロなら
  **フリーランキャリア**（位相ドリフト）が疑わしい。

判定が根本対応の指針になります：周期量子化ならTX解像度を上げれば効く。位相ドリフト
なら**マーク毎のキャリア位相リセット**が必要。

## 観測結果（2026-06-18）

実行：80マーク、`CAP 530 530 4 33 38000`（ライブラリは JVC の 525µs を 53tick =
**530µs** に丸めるので、これはJVCの実出力そのもの）。

```
carrier period : mean 26.23us, within-mark sd 0.67us
cycles/mark    : [20, 21]   （20cyc 43本 / 21cyc 37本 -> ~54% / 46%）
carrier-on span: mean 517.9us, sd 10.28us, range 508..530us（≈±1キャリア周期）
```

判定：

- **キャリア周期は綺麗**（26.23µs≈38.1kHz、マーク内sd 0.67µs）。high/low幅
  （~8.7 / ~17.6µs）は **10µsティックの倍数ではない** → キャリアはRMT解像度より
  細かいクロックで生成。**周期量子化/TX解像度は原因ではなく、解像度を上げても周期は
  変わらない。**
- **同一マークのサイクル数が 20 と 21 のほぼコインフリップ**（530÷26.23=20.21）、
  ON期間は±1周期ぶれる。これは**フリーランキャリア**の指紋（マーク境界がランダムな
  位相で切れ、20 or 21 の完全サイクルを拾う）。**根本原因として確定。**

JVCでどっちに転ぶか：マーク毎に約半々。TSOP側では、21サイクル＝マーク長め→直後
スペース短め（~538µs、IRremoteESP8266の~594µs JVC窓内＝OK）、20サイクル＝マーク
短め→スペース長め（~620µs、窓超え＝NG）。JVCのデコードは**全ゼロ空白が594µs未満**で
成功するので、約半数のビットがNG側だと16bitフレームのどこかが必ず超える→大半失敗、
たまたま全ビットOK側に揃うと成功。`compat_matrix/irremoteesp8266_rx[JVC]` の ~1/5 と一致。

対策への示唆：マーク毎にキャリア位相を揃え、各マークが決定的な整数サイクルを持つように
する。ハードの `rmt_apply_carrier` は連続発振（マーク毎の位相リセットなし）なので、
有力な道は**キャリアをRMTシンボルとして明示エンコード**すること。これには ~8.7/17.6µs
の半周期を表現するため **~1µs解像度が必要**。つまり解像度は「いま周期がズレているから」
ではなく「**対策の前提**」として効いてくる。

### マーク幅スイープ（`CL_MARKS="510,520,530,540,550"`, 各120マーク）

| mark µs | mark/period | サイクル分布 | 少数派% | on-span sd |
|---|---|---|---|---|
| 510 | 19.45 | 19:34 / 20:86 | 28 % | 10.4 µs |
| **520** | 19.84 | 20:106 / 21:14 | **12 %** | **4.8 µs** |
| **530**(JVC) | 20.21 | 20:63 / 21:57 | **48 %** | **10.3 µs** |
| **540** | 20.60 | 20:15 / 21:105 | **12 %** | 8.1 µs |
| 550 | 20.98 | 21:85 / 22:35 | 29 % | 7.2 µs |

サイクル分布はマーク幅で連続的にシフト（on-span平均は+10µs刻みに正確に追従:
498→508→518→528→539µs）し、**ジッターは振動**する：~530µs（半整数サイクル）で
ほぼ50/50＝最悪、~520/~540µs（整数サイクル付近）で少数派~12%＝安定。**ライブラリは
JVCの525µsを10µsティックで530µsに丸め、最悪点に着地**している（on-span sd 10.3µs は
520µsの4.8µsの約2倍）。

要点2つ：(1) 安いミティゲーションとして、JVCの送出マークを~520µs（仕様525の許容内）に
寄せればジッターをほぼ半減できる——ただし~12%の残留（フリーラン位相）は消えない。
(2) 完全決定化には依然マーク毎の位相整合が必要で、正確な整数サイクル幅（≈524.4µs=20周期）
は10µsティックでは置けない——どちらも**細かい解像度＋シンボルエンコードキャリア**を指す。
