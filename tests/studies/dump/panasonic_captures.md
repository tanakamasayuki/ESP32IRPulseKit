# Panasonic AC フィールドマップ実測メモ

> 実機リモコン **型番 ACXA75C15870**（Model::JKE 系、byte23=0x80）を `tests/studies/dump/` のダンプツールで
> キャプチャした生データと差分解析。**正式なフィールドマップとステータスは SPEC §11.2、実装方針は
> DESIGN §13** にあり、本書はその裏取りエビデンス（生キャプチャ・差分・観測ノイズの記録）。
> ここにしか無い観測（byte22 bit1 の一時フラグ、byte25 の快適フラグ、この機種の実態など）も保持する。

全体バイト列は 27 バイト（frame1 = byte0..7、frame2 = byte8..26）。frame1 と
byte8..12 の preamble、byte20=0x60、byte23=0x80 はこの取得では常に固定。

## 実装方針（決定。実装はまだ未着手）

- **実装する（常に使う制御フィールド）**: 0.5℃（byte22 bit7）/ 風向（byte16 下位）/
  しずか（byte21 bit5）/ パワフル（byte21 bit0）。
- **実装しない（setter を作らない）**: タイマー入/切、内部クリーン等の短縮コマンド。
  理由: コントローラ側が必要時に電源ON/OFFを送る方がリモコンライブラリとして素直
  （スケジューリングは送信側の責務）。タイマーは絶対時刻系の可能性が高く、正しく使うには
  時計合わせフレームも要る＝コスパが悪い。どうしても実機フレームを再送したい場合は
  RAW replay で代替できる。
- **ただし「無視」ではなく「触らない」**: フィールドマップは本書に残す。
  (1) デコード時に誤読/破壊しない、(2) エンコーダが setter から組むフレームで
  byte13 タイマービット=0・byte18-20=sentinel を保ち、タイマービットを汚さないため。
  読み取り専用の `onTimer()`/`offTimer()` 公開は任意（必須ではない）。

## 確定（複数サンプルで裏取り済み）

| フィールド | 位置 | コード/規則 | 実装状態 |
|---|---|---|---|
| power | byte13 bit0 | on=1 / off=0 | 実装済（`kOffMode`） |
| mode | byte13 上位ニブル | cool=3 / dry=2 / heat=4（auto=0 想定） | 実装済 |
| 整数℃ | byte14 | `floor(temp) << 1`、範囲 **16–30℃** | 実装済（`kOffTemp`） |
| **0.5℃** | **byte22 bit7 (0x80)** | セットで +0.5℃ | **未実装** |
| fan（風量） | byte16 上位ニブル | auto=A / 弱=3 / 弱+=4 / 中=5 / 強=6 / 最強=7 | 実装済（`kOffFan`） |
| **風向(louver)** | **byte16 下位ニブル** | 1〜5=固定位置 / F=auto | **未実装（同 byte16 の下位）** |
| **しずか/パワフル** | **byte21 bit5 / bit0** | しずか=0x20 / パワフル=0x01（fanニブルは0xAのまま） | **未実装** |
| checksum | byte26 | frame2（byte8..25）の総和 mod 256 | 実装済 |

- 0.5℃: .5 の温度は byte22 が必ず `0x80`、.0 は bit7=0。`temperatureC()` は
  `byte14>>1` しか見ないので 0.5 を落とす。
- 風向: fan と同じ byte16 の下位ニブル。現アクセサ未公開（コメント上は既知）。
- **しずか/パワフル は fan 速度とは別フィールド**（専用ボタン、fan=auto を保つ）。
  byte21 のビットで表現する。一方ライブラリの `Fan` enum は `QUIET`/`POWERFUL` を
  byte16 上位ニブル(3/7)として持つ（IRremoteESP8266 由来）。**実機は byte21 フラグなので
  食い違う**——実装時に要整理。

## byte21 のビット（判明分）

base = 0x40（cool/dry）。

- bit6 (0x40): cool/dry で 1、**heat で 0**（前回の heat=0x00 と整合）
- bit5 (0x20): しずか(Quiet)
- bit0 (0x01): パワフル(Powerful)

## mode 非依存の確定

- **風向（byte16 下位）と しずか/パワフル（byte21 bit5/bit0）は mode 非依存**。
  heat でも cool と同じ値・同じビットで動くことを確認（heat 16℃で風向1〜5/auto、
  風量3/4/5/7、しずか=byte21 0x20、パワフル=byte21 0x01）。byte21 は完全分解済み:
  bit6(0x40)=cool/dryで1・heatで0、bit5=しずか、bit0=パワフル。

## 解決済みの注意点

- **byte22 bit1 (0x02) = 温度ボタンを上限/下限ストッパーに当てたときの一時フラグ**
  （持続する設定ではない）。DRYの温度スイープで判明: 同じ「DRY・ON・16.0℃」が、
  下限に押し当てて到達したとき `byte22=02`、電源ONの素の状態だと `byte22=00` の
  2通り出た。cool の 30.0/16.0 で出ていたのもスイープで端に押し当てたため。
  **→ エンコーダではこのビットは常に 0 でよい（無視可）。** DRY も cool と同じく
  温度＋0.5℃を持つ（温度無効化する機種ではない）。
  **heat の温度スイープでも全て再確認済み**（範囲 16〜30℃、0.5℃あり、限界フラグの
  mode非依存、heat では byte21=0x00 / byte25=0x06 が全温度で一定）。温度は cool/dry/heat
  の3モードで確定 → これ以上の温度キャプチャは不要。

## この機種の実態 / 残り

- **この機種には mode=auto / fan が無い**（cool/dry/heat のみ）。**ナノイー/エコも無い**。
  → 通常運転の状態フレームのフィールドは出揃った（リバースエンジニアリング実質完了）。
  `Fan`/`Mode` enum 側に AUTO/FAN 等があっても、この機種は単に使わないだけ（superset）。
- **未押下のボタン = 診断 / 本体リセット / リセット / メニュー**。いずれもサービス/設定系で
  通常制御フレームとは別物の可能性が高い（メニューは無送信かも、診断/リセットは特殊コードや
  短縮フレームの可能性）。制御ライブラリ用途としては優先度低。気になれば1ボタン1ラベルで採取。

## 未解明（残りの細かい点）

- **byte23=0x80**: SPEC は JKE=0x81 / DKE=0x01 と記載。この機種は 0x80 で一致しない。
  モデル判定の見直しか、byte23 が純粋なモデルマーカーでない可能性。
- タイマーの分が絶対時刻(0時起点)か相対カウントダウンか（時計設定キャプチャで確定可）。

## タイマー（入/切）— 全 verified

状態フレーム内に入(ON)・切(OFF)タイマーが入る。Panasonic 標準の 11bit・分単位
packing がこの実機でも一致。チェックサムも全件成立（OFF1h→0x09, ON1h→0x43 等）。

- **byte13 下位ニブル = 有効化ビット**: bit0=power / bit1=入(ON)タイマー有効 /
  bit2=切(OFF)タイマー有効。通常=0x1、切=0x5（power on+bit2）、入=0x2（本体OFF中なのでpower=0）。
- **入(ON)タイマー = 11bit 分**: `byte18`(下位8bit) + `(byte19 & 0x07) << 8`。
  1h→0x3C=60、2h→0x78=120。
- **切(OFF)タイマー = 11bit 分**: `(byte19 >> 4)` | `((byte20 & 0x7F) << 4)`。
  1h→60、2h→120、11h→660、12h→720。例: 12h=720 → byte20=0x2D(45)・byte19上位=0 → 45<<4=720。
- **未設定タイマー** は範囲外 sentinel（通常フレームの byte18=00/19=06/20=60 ≒ 1536分相当）。
- 分が「絶対時刻(0時起点)」か「相対カウントダウン」かは時計合わせ状態次第（Panasonic標準は
  絶対時刻）。「1時間→60」なので時計=0:00 か相対。時計設定キャプチャで確定可。

**byte21 bit0 = パワフル（確定）。タイマーは byte21/byte25 に影響しない**: 切替キャプチャ
`...35 2C 80 AF 00 78 00 2D 40 80 80 00 16 91`（cool・切タイマー12h有効・power on）で、
タイマーが現に有効なのに `byte21=40`（bit0クリア）・`byte25=16` だった。よって過去の
タイマー/クリーン解除フレームで bit0 が立っていたのは「パワフルが点きっぱなしだった」だけ。
→ byte21 bit0 はパワフル専用。タイマーは byte21 にも byte25 にも触らない。
**byte25 bit4 (0x10)** も確定: fan=auto＋特殊なし＋cool/dry の「快適/おまかせ」フラグで、
パワフル・手動ファン・しずかで落ちるが**タイマーでは落ちない**。

## 別メッセージ種別: 短縮コマンドフレーム（内部クリーン等）

「内部クリーン」ボタンは現デコーダで**デコード不可**。raw を手で解析した結果、
Panasonic 系（同じヘッダ約3456/1728、bitタイミング約432/432/1296、約10ms ギャップ、
2フレーム）だが**フレーム長が違う**ことが判明：

- frame1 = `02 20 E0 04 00 00 00 06`（8バイト、通常と同じ署名フレーム）
- frame2 = `02 20 E0 04 80 B2 32 6A`（**8バイト**。通常の状態フレームは19バイト）
- 合計 **16バイト**（通常の状態フレームは 8+19=27バイト）

チェックサム成立を確認: frame2 の byte0..6 の総和 `02+20+E0+04+80+B2+32` = 618 →
`& 0xFF = 0x6A` = frame2 末尾。Panasonic 系の総和チェックサムと一致。

デコーダが落ちる理由: `fromRaw` は frame2 を19バイト固定で要求するため、64bit しか
来ない短縮フレームで bit 数不一致になり false。**特殊ボタン（内部クリーン等）は状態
フレームとは別系統の短縮コマンドフレーム**。ペイロードは preamble `02 20 E0 04` の後の
`80 B2 32`。SPEC が未対応とする `Panasonic-AC32`（短縮32bit）かそれ系のコマンドの可能性。

ライブラリ実装上は別の `Frame` 型（状態フレームのモデル違いではない）。未デコードでも
RAW replay で再送は可能。特殊ボタンを集めると `80 B2 32` の意味を割り出せる。

**解除は短縮コマンドではない**: 内部クリーンの解除は専用コマンドではなく、通常の
電源OFF状態フレーム（27バイト）で行う。例（cool・power off・クリーン解除）:
`02 20 E0 04 00 00 00 06 02 20 E0 04 00 30 2C 80 AF 00 00 06 60 41 80 80 00 06 3E`
（byte13=30=cool/off、タイマーは未設定sentinel、byte21=41/byte25=06 ← 上記 byte21 bit0 保留案件）。
特殊機能は「ON=短縮フレーム / 解除=通常フレーム」の非対称構成。
